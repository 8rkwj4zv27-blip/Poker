# Direction history and rejected paths

This history exists to prevent a future agent from treating an older proposal as current approval.

## 1. Initial read-only audit

The project began as an audit of repeated shells, panels, buttons, CRTs, mechanical readouts, navigation, results and motion.

The owner's initial reference hierarchy was:

1. Main Menu for menu/shell character.
2. Production FOLD/CALL/RAISE for large actions.
3. Player-dashboard CRT behaviour.
4. Existing mechanical score/stack/jackpot treatments.
5. Production TABLE CLEARED and its stage/wheel machinery.

The audit was to preserve gameplay, Career state, saves, settings, statistics, assets and screen composition while building a reversible approval process.

## 2. First approved system decisions

The owner approved the following foundation:

- Main Menu is the canonical menu/shell reference.
- FOLD/CALL/RAISE are the canonical large-button reference.
- Main Menu display housing plus table CRT behaviour define the CRT direction.
- Pale blue means live/current table information.
- Green/amber means ordinary machine information.
- Warm gold means money, reward and restrained positive result.
- Coral/red means danger, defeat and destructive action.
- Text blinking is meaningful, not universal.
- TABLE CLEARED and RUN OVER must be positive/negative outcomes from one physical result-stage machine.
- “Scrolling wheel” means the existing large stage rolling between gameplay and major results.
- Hand Rankings is the eventual first migration.
- Settings remains a quieter utility sheet.
- Main Menu Continue is shelved.
- `assets/ui/` remains untouched.

## 3. UI Lab V1 — rejected presentation

V1 established a useful component inventory, but its invented beige/serif/typewriter presentation and fixed-colour assumptions were rejected.

Do not revive:

- beige museum/typewriter styling;
- a separate Lab typography system;
- a fixed green/mint/gold/cream identity;
- disconnected theme tokens.

## 4. UI Lab V2 — palette and extraction correction

V2 moved closer to the Main Menu and real Settings themes. The retained lesson was to extract real production construction faithfully and make palette-bearing properties respond to the existing theme system.

V2 was not production-approved.

## 5. UI Lab V2.1 — dashboard and hierarchy correction

The dashboard candidate changed layout too much. The owner locked production dashboard markup, geometry, information hierarchy, card placement, chip bay, betting module and table relationship.

The palette also needed restraint: theme hues belong mainly on cabinet materials, rims, highlights and selected controls while wells and glass remain close to neutral black.

V2.1 proposals for CRT strength and shared result chassis were exploratory, not final approval.

## 6. Preservation/recovery pass

The owner stopped the broad redesign because it was drifting away from Poker Faces.

Explicitly rejected:

- redesigned dashboard composition;
- replacement cards and chips;
- generic clean UI;
- flattened pixel-art character;
- excessive thin outlines;
- shrinking TABLE CLEARED into a summary card;
- recolouring authored artwork with themes;
- turning every container into the same frame.

The owner wanted a physical pixel-art machine with clicks, clunks, CRT glass, real sprites and visible movement.

## 7. Simplified controlled Design Lab

The earlier `ui-lab.html` approach was replaced by `design-lab.html`: a plain internal comparison board with no archive deck, sliders, reference-image presentation or production navigation.

### Frames & Panels

F0–F6 were shown across all four real themes. The owner shortlisted:

- F0 Current Baseline
- F2 Padded Leather
- F3 Wood Rail
- F5 Layered Rim

No frame was approved. The owner later said isolated frame choice was difficult. The current strategy is to resolve frame traits inside a composite console.

### Buttons & Controls

An initial B0–B6 board varied mounting frames more than actual button design. The owner said B0 was best and B4 was acceptable, but the board was solving the wrong variable.

A second design-and-motion pass still pushed the mechanism too far into the cabinet.

The final controlled pass locked the B0 current-cartridge construction and compared restrained motion only. The owner selected:

- B0-C Soft Spring

The deepest motion was capped at four pixels. This selection applies to the menu/launch-style B0 specimen; it does not supersede the production live-table action family.

### CRT construction

C0–C6 compared physical tube and bezel construction. The owner selected:

- C0 Current Upgrade

### CRT effects

The construction was then locked to identical C0 screens. C0-A–C0-G varied only raster, phosphor and signal behaviour. The owner selected:

- C0-G Static Burst

The effect uses occasional fine static and a stronger finite burst during **Change Feed**. It has no moving glass-reflection sweep.

### Mechanical readouts

N0–N6 attempted new odometer, flap, drum, tile, brass, stepped and exposed-roller designs.

The owner rejected every option and asked to keep the game exactly as it was before. The family and its CSS/JavaScript were removed from the visible Design Lab.

Do not rebuild, archive or reinterpret those N0–N6 options. Existing production reels are canonical.

## 8. Current transition point

The owner accepted the recommendation to explore printed markings and physical label hierarchy next, then hand the work to Claude Code.

No printed-label board has been built yet.

## Consolidated “do not revive” list

- Beige, serif or typewriter UI direction.
- A hardcoded single-colour visual system.
- Palette-driven recolouring of cards, chips, faces, suits, logos or sprites.
- Redesigned dashboard geometry or replacement dashboard artwork.
- Moving glass-reflection animation.
- Universal text blinking.
- Excessive button push-through travel.
- Frame-heavy button boards that do not change the button itself.
- Any N0–N6 readout concept.
- A new mechanical-counter abstraction replacing production reels.
- Compressed or generic result cards replacing TABLE CLEARED.
- Main Menu changes or Continue-button fixes.
- Premature Hand Rankings migration.
- Production links, service-worker entries or app-shell entries for the Lab.
- A broad production CSS rewrite, framework migration or new dependency.
